# Spec Kit + Claude Code: шпаргалка

## Идея SDD в двух словах

Вместо «напиши мне приложение» вы проходите цепочку артефактов.
Каждый шаг — отдельный markdown-файл, который вы **читаете и правите**
перед следующим шагом:

```
constitution  →  spec  →  (clarify)  →  plan  →  tasks  →  (analyze)  →  implement
 принципы        ЧТО и     вопросы       КАК      шаги      проверка       код
 проекта         ЗАЧЕМ     к спеке      (стек)             согласованности
```

Главное правило: **spec — про «что» и «зачем», без технологий.**
Технологии появляются только на шаге plan.

## Что где лежит

| Путь | Что это |
|---|---|
| `.specify/memory/constitution.md` | «Конституция»: неизменные принципы проекта (тесты, простота, стек…) |
| `.specify/templates/` | Шаблоны spec/plan/tasks — можно менять под себя |
| `.specify/scripts/bash/` | Скрипты, которые вызывают команды (создание фичи, проверки) |
| `.specify/extensions/git/` | Расширение git: ветка на каждую фичу, опциональные автокоммиты |
| `.claude/skills/speckit-*` | Slash-команды для Claude Code |
| `specs/NNN-имя-фичи/` | Появится после `/speckit-specify`: spec.md, plan.md, tasks.md и др. |

## Команды

| Команда | Когда | Что получится |
|---|---|---|
| `/speckit-constitution` | один раз в начале | заполненный `constitution.md` |
| `/speckit-specify <описание>` | на каждую фичу | ветка `001-...` + `specs/001-.../spec.md` |
| `/speckit-clarify` | после specify (рекомендую) | Claude задаёт вопросы, ответы вписываются в spec |
| `/speckit-plan <стек>` | после spec | `plan.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md` |
| `/speckit-checklist` | опц., после plan | чек-листы качества требований |
| `/speckit-tasks` | после plan | `tasks.md` — пронумерованные задачи, `[P]` = можно параллельно |
| `/speckit-analyze` | опц., перед implement | отчёт о противоречиях между spec/plan/tasks |
| `/speckit-implement` | в конце | код по tasks.md, задачи отмечаются `[X]` |
| `/speckit-converge` | после implement | сверка кода со спекой, недоделки дописываются в tasks |
| `/speckit-git-commit` | когда угодно | коммит текущих изменений |

## Учебный проход (пример: консольный трекер привычек)

> Сначала **перезапустите Claude Code в этой папке**, чтобы он увидел skills:
> `cd ~/play/sdd-test && claude`

**1. Конституция**
```
/speckit-constitution Проект учебный. Принципы: простота важнее гибкости (YAGNI);
тесты обязательны для бизнес-логики; никаких внешних сервисов, данные хранятся
локально в файле; понятные сообщения об ошибках для пользователя.
```
→ Прочитайте `.specify/memory/constitution.md`. Не нравится — правьте руками или просите Claude.

**2. Спецификация (ЧТО, без технологий!)**
```
/speckit-specify Консольный трекер привычек. Пользователь может добавить привычку,
отметить её выполненной за сегодня, посмотреть список привычек с текущей серией
(сколько дней подряд выполнялась) и удалить привычку. Отметку за прошлые дни
ставить нельзя.
```
→ Откройте `specs/001-*/spec.md`. Обратите внимание на:
  - user stories с приоритетами (P1, P2…) — каждая должна быть самостоятельно полезной;
  - acceptance scenarios (Given / When / Then);
  - `[NEEDS CLARIFICATION: ...]` — места, где Claude не уверен.

**3. Уточнение**
```
/speckit-clarify
```
→ Ответьте на вопросы (обычно до 5). Ответы попадут в раздел Clarifications спеки.

**4. План (здесь — технологии)**
```
/speckit-plan Python 3, только стандартная библиотека, CLI через argparse,
хранение в JSON-файле, тесты на pytest. Управление зависимостями через uv.
```
→ Читайте `plan.md`: там есть **Constitution Check** — план сверяется с вашими принципами.

**5. Задачи**
```
/speckit-tasks
```
→ `tasks.md`: задачи сгруппированы по user story, тесты идут перед реализацией.

**6. Проверка (по желанию, но полезно)**
```
/speckit-analyze
```

**7. Реализация**
```
/speckit-implement
```
→ Claude идёт по задачам, отмечает `[X]`, запускает тесты.
Можно реализовывать по кускам: «/speckit-implement только фаза 1 и 2».

**8. Сверка и коммит**
```
/speckit-converge
/speckit-git-commit
```

## Советы новичку

- **Читайте каждый артефакт.** SDD работает, только если вы ревьюите spec и plan.
  Правка спеки стоит минуту, правка кода — гораздо дороже.
- **Ошибка в spec → правьте spec, а не код.** Plan и tasks потом правьте точечно
  (руками или попросив агента), а недостающие задачи пусть допишет `/speckit-converge`.
  Не перезапускайте `/speckit-plan` на готовой фиче: он затирает `plan.md` шаблоном.
- **Начните с маленькой фичи.** Цикл на большой задаче поначалу утомляет.
- **`/clear` между шагами — нормально.** Весь контекст лежит в файлах `specs/`.
- **Следующая фича** — снова `/speckit-specify ...`: появится ветка `002-...`.
- **Коммиты skills сами не делают**: hooks коммита в `.specify/extensions.yml` помечены
  `optional: true`, агент только предлагает. Автокоммиты: `auto_commit` в
  `.specify/extensions/git/git-config.yml` + `optional: false` у нужных hooks.
- Обновить Spec Kit:
  `uvx --from git+https://github.com/github/spec-kit.git specify self --help`

## План работы: каждая следующая доработка

**0. Подготовка.** `git checkout master`, рабочая директория чистая, тесты зелёные.

**1. Конституция.** Нарушает ли доработка принципы (сеть, сервер, база данных, новая
зависимость, авторизация, другой язык)? Если да → `/speckit-constitution <что и почему>`
→ прочитать → коммит. Если не уверены — идите дальше: противоречие поймает
Constitution Check на шаге plan.

**2. Спецификация.** `/speckit-specify <что и зачем, без технологий>` → ветка `00N-…` и
`specs/00N-…/spec.md`. Прочитайте целиком, ответьте на `[NEEDS CLARIFICATION]` → коммит.
Хорошее описание: для кого, что делает, зачем, что точно **не** входит.

**3. Уточнение.** `/speckit-clarify` → ответьте на вопросы. Не соглашайтесь на
рекомендацию, которую не понимаете, — переспросите → коммит.

**4. План.** `/speckit-plan <стек, библиотеки, ограничения>` → прочитайте `plan.md`
(особенно Constitution Check) и `research.md` → коммит.

**5. Задачи.** `/speckit-tasks` → просмотрите разбивку по фазам → коммит.

**6. Анализ.** `/speckit-analyze` → исправьте CRITICAL и HIGH в порядке spec → plan →
tasks → коммит. После серии правок запустите ещё раз.

**7. Реализация по фазам.** `/speckit-implement фазы 1–3` (MVP) → `npm run dev`,
посмотрите своими глазами → коммит. Затем следующая фаза и так далее.

**8. Сверка.** `/speckit-converge` → коммит задач → `/speckit-implement фаза N` → коммит.
Повторять, пока не будет «✅ Converged».

**9. Финал.** Ручная проверка по `quickstart.md` → `git checkout master` →
`git merge --no-ff 00N-…`.

### Когда полный цикл не нужен

| Ситуация | Что делать |
|---|---|
| Мелкий баг, поведение уже описано в спеке | Чинить сразу, с тестом. Spec Kit не нужен |
| Изменение поведения готовой фичи | Ветка → правка `spec.md` этой фичи (руками, попросив агента или через `/speckit-clarify`) → при необходимости `plan.md`/`research.md`/контракты → `/speckit-analyze` → `/speckit-converge` допишет задачи → `/speckit-implement` |
| Новая возможность | Новая фича: `/speckit-specify` → ветка `00N-…` |

### Размер фичи

Spec Kit лучше всего работает на фичах из 1–3 user stories: такую спеку и план
реально прочитать внимательно. Большую идею разбейте на несколько фич
(`002`, `003`, …) и вливайте их по очереди.

## Как вызывать каждую команду: шпаргалка «читай и делай»

Общее правило: **чем больше вы сами скажете на шагах constitution, specify и plan,
тем меньше агент будет решать за вас.** После каждой команды: прочитать результат →
поправить, если нужно → сказать «коммить».

### `/speckit-constitution` — принципы проекта

- **Когда:** в начале проекта или если новая фича противоречит принципам (сервер, сеть,
  база данных, новая зависимость, авторизация, другой язык).
- **Что писать:** 1–3 предложения — что меняется и почему. Названия технологий здесь
  допустимы: это правила проекта.
- **Пример:**
  ```
  /speckit-constitution Разрешить серверную часть для выполнения графов: сервер на Node.js
  использует тот же движок src/engine. Данные пользователя по-прежнему локальные,
  сервер хранит только результаты запусков. Причина — фича «выполнение на сервере».
  ```
- **После:** прочитать `.specify/memory/constitution.md` (раздел с изменённым принципом,
  номер версии) → «коммить».
- **Ошибка:** менять конституцию «на всякий случай». Меняйте, только когда правило
  реально мешает.

### `/speckit-specify` — спецификация новой фичи

- **Когда:** начало каждой новой фичи. Создаёт ветку `00N-…` и `specs/00N-…/spec.md`.
- **Что писать:** абзац на 5–15 строк, **без технологий**:
  1. для кого и что это (суть);
  2. главные сценарии: что пользователь делает и что получает;
  3. важные правила и ограничения;
  4. **что точно не входит** (сильнее всего сужает догадки агента).
- **Пример:**
  ```
  /speckit-specify Выполнение графов на сервере. Пользователь может отправить workflow
  на сервер и получить результат, не держа браузер открытым. Основной сценарий:
  нажал «Выполнить на сервере» — видит статус (в очереди / выполняется / готово / ошибка)
  и результат каждого нода, как в редакторе. Реактивность в браузере остаётся как есть.
  Результаты последних запусков хранятся и доступны после перезагрузки.
  Не входит: авторизация и несколько пользователей, расписания запусков,
  выполнение составных нодов на сервере по частям.
  ```
  Можно сослаться на файл: `/speckit-specify опиши фичу по ideas/server.md`.
- **После:** ответить на вопросы агента (не больше 3) → прочитать `spec.md` целиком:
  user stories, требования FR, критерии успеха SC, раздел Assumptions — там решения,
  которые агент принял за вас → «коммить».
- **Ошибка:** одна строчка. Тогда большую часть решений примет агент. Вторая ошибка —
  писать про технологии: им место в plan.

### `/speckit-clarify` — уточнение спеки

- **Когда:** сразу после specify (рекомендуется всегда).
- **Что писать:** ничего, команда без аргументов. Можно подсказать фокус:
  `/speckit-clarify особенно про обработку ошибок`.
- **Как отвечать:** агент задаёт до 5 вопросов по одному. Ответ — буква варианта, «yes»
  (принять рекомендацию) или свой короткий ответ. Свой вариант можно описать подробно.
- **После:** проверить раздел Clarifications в `spec.md` → «коммить».
- **Ошибка:** соглашаться на рекомендацию, которую не понимаете. Спросите «почему так»
  или «какие минусы» — это нормально.

### `/speckit-plan` — технический план

- **Когда:** после clarify.
- **Что писать:** стек и технические ограничения, 1–3 предложения. Не знаете стек —
  сначала попросите обычным сообщением: «сравни варианты стека для этой фичи».
- **Пример:**
  ```
  /speckit-plan Сервер на Node.js 24 + Fastify, движок src/engine переиспользуется как есть.
  Очередь запусков в памяти, результаты в SQLite. Клиент общается с сервером по HTTP + SSE
  для статусов. Тесты: Vitest для сервера, Playwright для сквозного сценария.
  ```
- **После:** прочитать `plan.md` — **Constitution Check** (все ли принципы пройдены),
  структуру файлов, таблицу обоснования зависимостей; `research.md` — решения и
  отвергнутые варианты → «коммить».
- **Ошибка:** перезапускать `/speckit-plan` на уже готовой фиче — он затирает `plan.md`
  шаблоном. Готовый план правьте точечно.

### `/speckit-checklist` — чек-лист качества требований (по желанию)

- **Когда:** после plan, если хочется проверить спеку по конкретной теме.
- **Что писать:** тему проверки: `/speckit-checklist безопасность и обработка ошибок`.
- **После:** пройти пункты чек-листа сами. `[x]` означает «требование описано хорошо»,
  а не «реализовано».

### `/speckit-tasks` — список задач

- **Когда:** после plan.
- **Что писать:** ничего. Можно попросить особенности:
  `/speckit-tasks тесты обязательно, MVP — только первая user story`.
- **После:** просмотреть `tasks.md` — фазы по user stories, тесты перед реализацией,
  пути к файлам → «коммить».

### `/speckit-analyze` — проверка согласованности

- **Когда:** после tasks, перед реализацией. И после любой серии правок артефактов.
- **Что писать:** ничего. Команда только читает файлы и ничего не меняет.
- **После:** в отчёте смотреть **CRITICAL и HIGH** — их исправить до реализации.
  Сказать «да, предлагай правки» → обсудить решения → правки вносятся в порядке
  spec → plan → tasks → «коммить» → запустить analyze ещё раз.
- **Ошибка:** пропустить этот шаг. На нашей фиче он нашёл риск потери данных
  при смене папки — до написания кода.

### `/speckit-implement` — реализация

- **Когда:** после analyze без CRITICAL/HIGH.
- **Что писать:** какие фазы делать. **Не берите всё сразу.**
  ```
  /speckit-implement только фазы 1–3 (Setup, Foundational, US1)
  /speckit-implement фаза 4 (US2)
  ```
- **После каждой фазы:** `npm run dev` и посмотреть своими глазами; убедиться, что
  тесты зелёные (агент покажет) → «коммить» → следующая фаза.
- **Обратить внимание:** раздел «Отклонения от плана» в отчёте агента — что пошло
  не так, как планировали, и записано ли это в артефакты.

### `/speckit-converge` — сверка кода со спекой

- **Когда:** после реализации всех фаз.
- **Что писать:** ничего.
- **Что происходит:** агент сравнивает код со спекой, планом и конституцией и
  **дописывает задачи** в конец `tasks.md` (новая фаза Convergence). Код он не меняет.
- **После:** прочитать находки → решить спорные пункты (например, «вписать в спеку
  или убрать») → «коммить» → `/speckit-implement фаза N` → «коммить» →
  `/speckit-converge` снова. Повторять, пока не будет «✅ Converged».

### `/speckit-git-commit` — коммит (по желанию)

- То же, что сказать агенту «коммить». Агент сам коммитит только по вашей команде.

### `/speckit-taskstoissues` — задачи в GitHub Issues (по желанию)

- **Когда:** если работаете командой и ведёте задачи в GitHub.
- **Что писать:** ничего; нужен настроенный `gh` и remote на GitHub.
- **После:** проверить созданные issues в репозитории.

### Изменение уже готовой фичи (без отдельной команды)

1. `git checkout -b 001-<что-меняем>`.
2. Поправить `spec.md` этой фичи: руками, обычной просьбой агенту
   («обнови в спеке 001 FR-021a: …») или через `/speckit-clarify`.
   Добавить строку в Clarifications: что и почему изменилось.
3. При необходимости поправить `plan.md`, `research.md`, контракты.
4. `/speckit-analyze` → `/speckit-converge` (допишет задачи) → `/speckit-implement фаза N`.
5. «коммить» → «влей в master, запушь и удали ветку».
