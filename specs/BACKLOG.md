# Backlog: отложенные фичи

Фичи, о которых договорились, но которые ещё не начаты. Соглашение проекта, не артефакт
Spec Kit.

## Правила

- Если в ходе фичи договорились вынести часть работы на потом — сразу добавить сюда
  запись по шаблону ниже, а в `spec.md` текущей фичи записать, что это вне её рамок.
- Новая фича начинается на `master`: сначала свериться с этим файлом, затем
  `/speckit-specify` с текстом из поля «Описание для /speckit-specify».
- Начатая фича удаляется отсюда в том же коммите, где появляется её `spec.md`; источником
  истины становится каталог `specs/NNN-…/`. Номер фичи выдаёт `/speckit-specify`.
- Две фичи, меняющие одни и те же файлы, не ведутся параллельно: следующая начинается
  после слияния предыдущей.

Шаблон записи (`## Название`):

- **Статус**: `договорились` — описание готово, ждёт условия начала; `требует решения` —
  сначала анализ, возможный итог «не делать».
- **Откуда**: обсуждение или шаг фичи, где появилась договорённость, с датой.
- **Когда начинать**: условие или событие.
- **Описание для /speckit-specify**: что и зачем, без технологий.
- **Заметки к плану**: технические решения и ограничения, уже принятые в обсуждении.
- Для статуса «требует решения» — ещё **Что решить**: варианты, «за» и «против».

## Защита сервера выполнения

- **Статус**: договорились.
- **Откуда**: обсуждение архитектуры удалённого engine (2026-10-07). В первой фиче
  сервер осознанно открыт для любого Origin: WebSocket без проверки `Origin`, HTTP-ответы
  с `Access-Control-Allow-Origin: *`. Сейчас это безопасно: ноды чистые, документы
  изолированы по соединению, сервер ничего не хранит.
- **Когда начинать**: обязательно до фичи, которая даёт нодам на сервере эффекты
  (`fetch`, файлы и т. п.) или общее состояние между соединениями. Без неё такие
  возможности не включать.
- **Описание для /speckit-specify**: Защита сервера выполнения workflow от
  посторонних клиентов. Сайты, открытые в браузере пользователя, и программы в сети
  не должны без разрешения запускать workflow на сервере и пользоваться его
  возможностями. Пользователь решает, какие клиенты допускаются.
- **Заметки к плану**: проверка заголовка `Origin` при WebSocket-рукопожатии (список
  разрешённых, флаг CLI) защищает только от сайтов в браузере (cross-site WebSocket
  hijacking); от программ вне браузера — токен / аутентификация (нужна поправка к
  конституции: раздел «Ограничения»). Учесть DNS rebinding (проверка `Host`).

## Каталог нодов от цели вычисления

- **Статус**: договорились.
- **Откуда**: clarify фичи 004 (2026-10-07). В 004 палитра и проверки связей идут по
  встроенному каталогу редактора; при подключении сверяется только версия протокола.
  Если у сервера другой набор нодов, незнакомый ему нод показывает ошибку неизвестного
  типа. Вариант «скачивать код engine с сервера» отклонён: чужой код получил бы доступ
  к данным и рабочей папке пользователя.
- **Когда начинать**: вместе с фичей о серверных нодах с возможностями (сеть, файлы)
  или раньше, если расхождение каталогов редактора и сервера начнёт мешать.
- **Описание для /speckit-specify**: Палитра и проверки связей следуют за целью
  вычисления. Цель сообщает, какие ноды она умеет вычислять (названия, категории,
  порты); палитра показывает именно их, связи проверяются по их портам. При смене цели
  палитра меняется; ноды, которых нет у цели, явно помечены в открытых workflow. Без
  связи редактор пользуется последним известным каталогом цели.
- **Заметки к плану**: каталог передаётся данными в `welcome` (описания нодов без
  `compute`), не кодом. Правила графа уже работают от `NodeRegistry`. Кэш каталога —
  рядом с настройкой цели (IndexedDB). Правила совместимости типов портов остаются
  частью версии протокола.

## Редактор отдельным пакетом и название designer

- **Статус**: требует решения — до `/speckit-specify` рассмотреть плюсы, минусы и
  целесообразность; возможный итог — «не делать».
- **Откуда**: plan фичи 004 (2026-10-07). В 004 редактор оставлен в корне репозитория
  (пакет `dagflow`) рядом с `packages/engine`, `protocol`, `server` — ради экономии
  переноса (research R1 фичи 004).
- **Когда начинать**: после слияния 004 (меняет те же файлы: конфиги, `src/`, `tests/`).
  Не раньше, чем решение принято.
- **Что решить**:
  1. Переносить ли веб-клиент в отдельный пакет (`packages/designer`).
     - «За»: корневой `package.json` перестаёт совмещать настройку монорепо и
       зависимости клиента; границы через `exports` нельзя обойти относительным
       импортом; четыре пакета-соседа нагляднее.
     - «Против»: перенос ~120 файлов и правка `vite.config.ts`, `playwright.config.ts`,
       `tsconfig.json`, `eslint.config.js`, `.github/workflows/pages.yml`, команд в
       `CLAUDE.md`; для пользователя ничего не меняется.
  2. Переименовать «редактор / editor» в **designer** — UI веб-клиент для просмотра и
     редактирования графов: в коде, именах пакетов и папок, артефактах Spec Kit,
     `CLAUDE.md`, README; решить, меняется ли что-то в текстах интерфейса.
- **Описание для /speckit-specify** (если решено делать): Веб-клиент для просмотра и
  редактирования графов называется designer и живёт отдельным пакетом монорепо рядом
  с engine, protocol и server. Поведение для пользователя не меняется.
- **Заметки к плану**: `git mv` одним коммитом без изменения кода; затем правка
  конфигов и путей; все тесты зелёные без изменений поведения. Проверить, нужны ли
  пометки «переименовано» в спецификациях 001–004 или достаточно замены терминов.
