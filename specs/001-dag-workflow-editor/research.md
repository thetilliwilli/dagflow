# Research: Визуальный редактор и реактивная среда выполнения DAG-workflow

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-10-05

Каждое решение оформлено как Decision / Rationale / Alternatives considered.
Версии пакетов проверены в npm registry 2026-10-05.

## R1. Стек и версии

**Decision**: TypeScript 6.0, React 19.3, @xyflow/react 12.12, Zustand 5.0, Immer 11.1,
Valibot 1.5, idb-keyval 6.3, Vite 8.3 (+ @vitejs/plugin-react 6.1), Vitest 5.0,
@testing-library/react 16.3, @playwright/test 1.63, Node.js 24 LTS для разработки.

**Rationale**: стек выбран пользователем (вариант A сравнения). TypeScript 6.0, а не
7.0: typescript-eslint 8.71 поддерживает только TypeScript `<6.1`, а ESLint нужен для
изоляции движка (уточнено на шаге implement, 2026-10-05). React Flow — самая
зрелая библиотека холста для редакторов нодов. TypeScript нужен для типобезопасного
описания портов и графа.

**Alternatives considered**: Svelte 5 + Svelte Flow, Vue 3 + Vue Flow / Rete.js,
LiteGraph.js. Отклонены на этапе сравнения: меньше экосистема или встроенный движок,
не совпадающий с реактивной семантикой спеки.

## R2. Алгоритм реактивного вычисления

**Decision**: свой инкрементальный движок с пересчётом в топологическом порядке:

1. Любое изменение (значение входа, связь, нод) помечает изменённые ноды «грязными».
2. Грязным становится и всё, что достижимо от них по связям (потомки).
3. Грязные ноды пересчитываются один раз в топологическом порядке (алгоритм Кана
   на подграфе грязных нодов). Нод вычисляется только после всех своих источников,
   поэтому смешения старых и новых значений (глитча) не бывает (FR-013).
4. Чистые ноды сохраняют кэшированные выходы (FR-012).

Функции вычисления встроенных нодов синхронные и чистые:
`(inputs) => outputs | throw NodeError`. Изменения копятся и сбрасываются в движок
пакетом раз в кадр (`requestAnimationFrame`). Это объединяет быстрые правки, например
набор числа по символу, и даёт состояние «вычисляется» для нодов, ожидающих
пересчёта в текущем пакете (FR-016, edge case о быстром вводе). Стабильный порядок
обхода и чистые функции делают результат детерминированным (FR-014).

**Rationale**: семантика спеки (глитч-фри, частичный пересчёт, автоматическое
восстановление после ошибки) реализуется напрямую и тестируется без UI. Реализация
занимает несколько сотен строк.

**Alternatives considered**:
- signals (@preact/signals-core, alien-signals): глитч-фри из коробки, но структура
  графа меняется на лету, и пришлось бы синхронизировать две модели данных;
- RxJS: `combineLatest` даёт глитчи, тяжёлая зависимость;
- асинхронные ноды с отменой: не нужны, встроенные ноды мгновенные (принцип I).
  Если понадобятся (например, для серверного выполнения), добавятся поверх
  номера ревизии пакета.

## R3. Составные ноды при вычислении

**Decision**: перед вычислением граф workflow «разворачивается»: каждый экземпляр
составного нода рекурсивно заменяется копией внутреннего графа с идентификаторами
вида `instanceId/innerNodeId`. Ноды «Вход» и «Выход» становятся сквозными
(passthrough) нодами. Результаты для отображения собираются обратно: выходы
экземпляра берутся из нодов «Выход», а состояние экземпляра агрегируется по
внутренним нодам по приоритету: есть `error` → `error`, иначе есть `waiting` → `waiting`, иначе есть `blocked` → `blocked`, иначе есть `computing` → `computing`, иначе `ok` (сводный статус показывает первопричину, а не её следствия).

Развёрнутый граф строится заново только при изменении структуры: нодов, связей или
определений составных нодов. Изменение значения входа такой перестройки не требует.

Рекурсия (составной нод внутри самого себя) запрещается при редактировании:
проверяется обходом графа зависимостей определений (FR-026).

**Rationale**: движок работает с одним плоским DAG, и все гарантии R2 автоматически
распространяются на вложенные ноды.

**Alternatives considered**: вложенное вычисление (каждый составной нод — отдельный
подграф со своим движком). Отклонено: сложнее гарантировать отсутствие глитчей и
частичный пересчёт через границы составных нодов.

## R4. Типы и проверка связей

**Decision**: тип порта — одно из `number | text | boolean | array | object | any`.
Связь разрешена, если `source.type === target.type || source.type === 'any' ||
target.type === 'any'` (FR-005a). Цикл проверяется при соединении: ищем, достижим
ли `source` из `target` (DFS, O(V+E)). Значения, введённые вручную, проверяются на
соответствие типу порта при вводе. Значения, пришедшие по порту `any`, проверяет
сам нод: неподходящее значение даёт `NodeError` с сообщением (FR-005b).

**Rationale**: самая простая схема, удовлетворяющая SC-004.

**Alternatives considered**: JSON Schema для портов. Отклонено на шаге clarify.

## R5. Состояние приложения и undo/redo

**Decision**: один Zustand-стор со срезами `workspace` (список workflow, определения
составных нодов, хранилище), `tabs` (открытые вкладки, активная) и `history`
(своя для каждой вкладки). Документ графа неизменяемый, правки делаются через Immer
`produce`. История — стек снапшотов документа (структурное разделение делает их
дешёвыми), не больше 100 шагов на вкладку. Серия правок одного поля значения
объединяется в один шаг, если между правками прошло меньше 500 мс.

Редактирование составного нода открывается в отдельной вкладке вида `composite`
со своей историей. История относится только к графу вкладки: отмена сворачивания
возвращает группу нодов, а созданное определение остаётся в палитре; действия
палитры (переименование, удаление) в историю не входят (FR-009). Изменения определения сразу видны во всех вкладках (FR-031b),
потому что определения лежат в общем срезе `workspace`.

Состояние вычисления (NodeState) хранится отдельно от документа и в историю не
попадает.

**Rationale**: снапшоты проще патчей (принцип I), Immer даёт неизменяемость без
шаблонного кода, а React Flow сам построен на Zustand.

**Alternatives considered**: Immer `produceWithPatches` и хранение патчей (экономнее
по памяти, но сложнее), zundo (лишняя зависимость ради простого стека), Redux
Toolkit (тяжелее).

## R6. Интеграция с React Flow

**Decision**: React Flow работает в управляемом режиме: `nodes` и `edges` выводятся
из документа активной вкладки, события `onNodesChange`, `onConnect` и т. п.
превращаются в действия стора. Проверка связи делается через `isValidConnection`,
который вызывает функцию движка `canConnect` (FR-004, FR-005a), причина отказа
показывается подсказкой. Кастомный компонент нода рисует порты (`Handle`, id =
имя порта) с типом и текущим значением. Компонент мемоизирован и подписан
селектором только на состояние своего нода, поэтому изменение одного значения не
перерисовывает весь граф (SC-002, SC-003).

**Rationale**: стандартный и документированный путь работы с React Flow.

**Alternatives considered**: неуправляемый режим (внутреннее состояние React Flow).
Отклонено: undo/redo и сохранение требуют, чтобы источником истины был наш
документ.

## R7. Хранение: рабочая папка и запасной вариант

**Decision**: один класс `DirectoryStorage` поверх `FileSystemDirectoryHandle`.
Этот интерфейс одинаков у папки пользователя (`window.showDirectoryPicker`, File
System Access API) и у OPFS (`navigator.storage.getDirectory()`), поэтому реализация
одна, а меняется только источник дескриптора.

- Дескриптор выбранной папки сохраняется в IndexedDB через idb-keyval (дескрипторы
  сериализуемы через structured clone).
- При старте: `queryPermission({mode: 'readwrite'})`. Если `granted`, работаем с
  папкой. Если `prompt`, показываем экран восстановления доступа (нужен жест
  пользователя для `requestPermission`). До подтверждения **ничего не загружаем и
  не пишем**, поэтому данные не могут разойтись. На экране есть явный выбор
  «Работать в браузере»: он переключает хранилище на OPFS, а данные папки не
  трогает (FR-028d).
  *Отвергнуто*: работать в OPFS до подтверждения и потом сливать изменения в
  папку — нужны правила разрешения конфликтов; режим «только чтение» — нужен кэш.
- Если API нет (Firefox, Safari) или пользователь отказался, используется OPFS
  (FR-028b). В интерфейсе показывается индикатор текущего хранилища.
- Смена хранилища (FR-028c):
  - новая папка пуста → по подтверждению копируем в неё все данные текущего
    хранилища;
  - в папке уже есть данные редактора → загружаем их; workflow из текущего
    хранилища, которых нет в папке (по id), предлагаем добавить в конец списка;
    workflow с тем же id, но другим содержимым (канонический JSON графа и имени)
    предлагаем добавить копией «&lt;имя&gt; (из браузера)» с новым id;
    составные ноды сливаются той же функцией, что и при импорте (FR-029a,
    `src/model/import.ts`); существующие файлы папки не перезаписываются.
- Автосохранение: запись через 300 мс после последнего изменения, плюс сброс
  несохранённого на `visibilitychange`/`pagehide`. Укладывается в SC-008 (< 1 с).
- Запись атомарна в пределах файла: `createWritable()` пишет во временный файл и
  подменяет при `close()`.

**Rationale**: один путь кода для обоих хранилищ и минимум зависимостей.

**Alternatives considered**: localStorage (лимит около 5 МБ, синхронный) и
IndexedDB как основное хранилище (данные не видны пользователю как файлы).
Отклонены.

**Риски**:
- `createWritable()` для OPFS поддерживается в Chromium и Firefox; в Safari
  поддержка появилась недавно. Если в целевой версии Safari её нет, нужен запасной
  путь записи через Web Worker и `createSyncAccessHandle()`. Проверить на этапе
  реализации (задача в tasks.md).
- Права на папку могут сбрасываться браузером между визитами. Это обрабатывается
  баннером восстановления доступа.

## R8. Форматы файлов и импорт

**Decision**: JSON-файлы с полями `format` и `version` для миграций. Раскладка
рабочей папки — один файл на workflow и один на определение составного нода (см.
[contracts/file-formats.md](./contracts/file-formats.md)). Файл выгрузки
самодостаточен: workflow плюс все транзитивно используемые определения составных
нодов (FR-029).

Импорт проходит в три шага:
1. Структурная проверка Valibot-схемой.
2. Семантическая проверка: неизвестные типы нодов, циклы, несовместимые типы
   связей, рекурсия составных нодов.
3. Слияние определений по FR-029a: совпадение определяется по каноническому JSON
   (ключи отсортированы, без служебных полей).

При любой ошибке список workflow не меняется (FR-030).

**Rationale**: Valibot даёт типобезопасную проверку с понятными путями ошибок при
малом размере бандла.

**Alternatives considered**: Zod (больше бандл), ручная проверка (много кода и
ошибок).

## R9. Тестирование

**Decision**:
- Vitest (окружение node): движок, проверка связей, составные ноды, встроенные
  ноды, форматы и импорт. Это основной объём тестов (принцип II).
- Vitest (окружение jsdom) + Testing Library: стор и ключевые компоненты (нод,
  палитра, вкладки, сообщения об ошибках).
- Хранилище тестируется на фейке `FileSystemDirectoryHandle` в памяти.
- Playwright (Chromium) для e2e по user stories. OPFS в Chromium работает
  по-настоящему. `showDirectoryPicker` подменяется через `addInitScript` на
  дескриптор OPFS: выбор папки так тестируется без системного диалога.
- Каждый acceptance-сценарий спеки сопоставлен минимум одному тесту (матрица в
  tasks.md).

**Rationale**: логика вынесена из UI, поэтому большинство сценариев проверяется
быстрыми unit-тестами, а e2e остаются для сквозных потоков.

**Alternatives considered**: Vitest browser mode вместо jsdom. Возможен позже,
сейчас jsdom проще.

**Уточнение (implement, 2026-10-05)**: Chromium падает при чтении из IndexedDB
сохранённого `FileSystemDirectoryHandle` в изолированных («инкогнито») контекстах,
которые Playwright создаёт по умолчанию; в постоянном профиле всё работает (проверено
на headless shell и полной сборке). Поэтому сценарии US3 с рабочей папкой запускаются
через фикстуру `tests/e2e/persistent.ts` с постоянным профилем на каждый тест.

## R10. Встроенные ноды

**Decision**: минимальный набор по FR-010 описан в
[contracts/builtin-nodes.md](./contracts/builtin-nodes.md). Явные ноды
преобразования («В текст», «В число») есть, автоматических преобразований нет
(FR-005a).

**Rationale**: покрывает все категории FR-010 и даёт достаточно для примеров из
спеки (сложение, деление на ноль, «удвоенная сумма»).

**Alternatives considered**: ноды с переменным числом портов (например, «Собрать
массив» на N входов). Отложено: усложняет модель портов без требования в спеке.
