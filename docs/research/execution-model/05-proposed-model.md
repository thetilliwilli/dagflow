# Предлагаемая модель: событийное ядро + данные по требованию (2026-10-10)

Модель Unreal Blueprints и Houdini/TouchDesigner («cook on demand»): формально DEVS для
событий и pull с мемоизацией для данных.

## Три вида нодов

- **Чистый нод** (pure). Только порты данных, синхронная функция без эффектов. Не
  исполняется сам; считается, когда его выход кто-то запросил; результат кэшируется до
  инвалидации входов.
- **Исполняемый нод** (exec). Есть входной сигнальный порт. Срабатывает на каждое
  пришедшее событие: вытягивает входы данных как снимок, делает работу (эффект, запись),
  испускает сигналы на выходах, может выставить выходы данных («последний результат»).
- **Латентный нод** (latent). Исполняемый нод, завершающий работу не сразу: таймер, HTTP,
  ожидание. Испускает сигнал «готово» в будущем через очередь событий.

## Два вида связей

- **Данные.** Без циклов. Семантика pull: потребитель спрашивает источник. Изменение
  источника только помечает потомков «устарел». Pull glitch-свободен по построению:
  D спрашивает B и C, оба спрашивают A, все видят одно A. Ромбы любой глубины правильны
  без топологической сортировки и батча.
- **Сигналы.** Циклы разрешены. Событие — запись в очереди с меткой (виртуальное время,
  порядковый номер), доставка строго по метке. Кольцо — цепочка событий, не рекурсия.

## Ядро

Одна очередь событий на виртуальном времени. Тик: взять события с меткой времени не
больше `now`, доставить по порядку; срабатывание exec-нода может породить события в это
же мгновение (в хвост) или в будущее. Движок возвращает адаптеру «следующее событие
в T», адаптер ставит таймер и зовёт `tick(now)`. Движок часы не читает.

## Почему pull, а не батч

Батч считает всё затронутое после каждого изменения. Pull умеет и это, и ленивость через
политику «кого тянуть», которая живёт снаружи ядра:

- только то, что запросил сигнал — HTTP в данных не стреляет при правке константы, пока
  до него не дошло исполнение;
- выделенный нод для окна свойств;
- ноды-стоки (Output, Show) после каждого тика;
- всё — прежнее поведение фичи 001.

## Чего нет нарочно

- **Асинхронных нодов данных.** HTTP — латентный exec-нод: сигнал на вход, через время
  сигнал «готово», результат в выходном порте данных. Иначе pull становится
  асинхронным, ломается glitch-свобода, нужны поколения внутри слоя данных. При нужде
  добавляется как сахар: exec-нод с автотриггером при устаревании входов.
- **Срабатывающих данных.** Нет вопроса «какой вход триггер», нет горячих/холодных
  входов. Триггер всегда сигнал, данные всегда снимок.
- **Глобального такта.** Время двигают только события; пустой граф ничего не потребляет.

## Что определить в spec

1. Мгновение и порядок: события с одним временем — по порядковому номеру; кольцо без
   задержки — лимит переходов за мгновение или запрет в редакторе (в каждом сигнальном
   цикле должен быть латентный нод).
2. Несколько сигналов в один exec-нод: каждое событие — отдельное срабатывание; ожидание
   нескольких — явный нод Join / Gate.
3. Правка графа во время полёта: удаление нода отменяет его латентную работу; правка
   входов не трогает (входы читаются в момент срабатывания); связи — решить.
4. Состояние выполнения вне файла: очередь, кэши, таймеры не сохраняются и не передаются
   при переподключении; сигнальная часть стартует заново, данные — по требованию.
5. Выходы данных у exec-нода: «последний результат»; до первого срабатывания — «нет
   значения» со статусом ожидания у потребителя.
6. Старт: нод Start при открытии документа, кнопка, внешнее сообщение.
7. Детерминизм: данные — функция графа; сигналы — функция графа и последовательности
   внешних событий с временами; conformance на виртуальных часах с записанной
   последовательностью.

## Запасной вариант

Однородная событийная симуляция с дельта-циклами (данные — связи с нулевой задержкой).
Меньше понятий, но нет ленивости и есть повторные пересчёты внутри мгновения; не
подходит именно из-за HTTP-нодов, которым ленивость нужна больше всего.
