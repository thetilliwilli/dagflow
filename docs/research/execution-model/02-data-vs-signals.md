# Данные и сигналы: почему два вида портов (2026-10-10)

## Гипотеза пользователя

«Data-порт это частный случай сигнального: сигнал с правилом "запомни значение". Сделаем
все порты сигнальными с флагом сохранять / не сохранять, и система покроет все случаи».

Рассуждение верное наполовину. В FRP так и устроено: Behavior получается из Event
операцией `hold`; в RxJS это `BehaviorSubject`; в Max/MSP холодные входы запоминают
пришедшее. Как **механизм реализации** одна очередь сигналов с флагом покрывает оба
случая. Изъян в другом: один бит не несёт остальных различий, а их несколько, и они
независимы.

## Семь независимых свойств

1. **Семантика соединения входов.** Для данных вопроса «когда считать D» нет: D всегда
   равен f(B, C). Для сигналов вариантов минимум три: `combineLatest`, `withLatestFrom`,
   `zip` (горячие и холодные входы Max). Нужен флаг «какой вход триггер».
2. **Одновременность и ромб.** Данные хотят одного пересчёта D со свежими B и C.
   Сигналы хотят, чтобы каждое событие дошло: два клика это два клика. Данные сливаются в
   тике (last-write-wins), события ставятся в очередь без слияния. Противоположные
   умолчания.
3. **Отсечение по равенству.** Нод выдал то же значение: для данных потомков можно не
   трогать, для событий то же значение дважды это два события.
4. **Повтор при подписке и загрузке.** «Запомнить» мало: нужно переотправить
   сохранённое новому потребителю и при открытии файла, иначе граф мёртв до первого
   изменения. Это `ReplaySubject(1)`, скрытая половина правила.
5. **Чистота и повторяемость.** Из пункта 4: всё, что ниже данных, может быть выполнено
   заново в любой момент, значит ноды данных обязаны быть чистыми. Обработчик события
   выполняется ровно один раз: HTTP POST, запись файла. Переотправка при переподключении
   запустила бы эффекты повторно.
6. **Зависимость от истории.** Состояние нода данных это функция текущего графа: сохранил
   файл, открыл, получил то же. Состояние счётчика событий это функция истории, которой в
   графе нет. На воспроизводимости из графа держится протокол (шлёт весь граф),
   conformance-тесты и пометка грязных по подписи.
7. **Триггер и значение.** У данных есть «сейчас», у события нет: оно произошло один раз
   и либо обработано, либо потеряно. Pull для событий невозможен по определению.

Комбинаций флагов много, практически осмысленных наборов два: «данные» и «сигналы».
Унификация правильна внутри движка и вредна в модели пользователя: он получит семь
ручек, почти все сочетания которых либо глитчат, либо дублируют эффекты.

## Подтверждение из практики

- **Flyde** (визуальное программирование на TypeScript, одна связь на всё) пришёл ровно к
  этим ручкам: входы `queued` и `sticky`, `reactive inputs` (перезапуск нода, пока он
  работает), `completion outputs` (явное завершение), отдельный вход Trigger, правило
  «нод ждёт все обязательные входы». Это свойства 1, 2, 4, 7 в виде настроек на каждом
  ноде.
- **Vuo** (один вид кабеля, событие плюс необязательные данные) добавил event walls и
  doors на входах, правило «нод ждёт все части разделённого события и исполняется один
  раз», запрет на повторное прохождение события по кабелю. Модель работает, но
  пользователь думает о событиях везде, включая арифметику.
- **Unreal Blueprints, Unity Visual Scripting, Ventuz, Rete.js** держат два вида связей
  (exec/flow и data; events/methods и bindings; control flow и dataflow) и живут с этим
  годами.

## Решение

Внутри движка один планировщик и одна очередь: данные это пометка «устарел» со слиянием
и pull, сигналы это записи FIFO. Снаружи два вида портов с фиксированными свойствами и
явные переходники: `Hold` (сигнал → данные: сохранить последнее значение) и `Changes`
(данные → сигнал при изменении). Переход между мирами виден на холсте, а не спрятан во
флаг порта.
