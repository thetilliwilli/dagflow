# Данные и сигналы: почему два вида портов (2026-10-10)

## Гипотеза

«Порт данных — частный случай сигнального порта с правилом „запомни последнее
значение“; сделаем все порты сигнальными с флагом сохранять / не сохранять».

Гипотеза верна как **механизм**. В FRP Behavior получается из Event операцией
`hold`/`stepper`; в RxJS это `BehaviorSubject`; в Max/MSP и Pure Data данных нет вовсе,
холодные входы просто запоминают пришедшее. Одна очередь сигналов с флагом «сохранять»
покрывает оба случая по выразительности.

## Что ещё различается

Один бит «сохранять» не несёт остальных различий, а они независимы друг от друга.

1. **Семантика соединения входов.** Для данных вопрос «когда считать D» не стоит:
   D = f(B, C) при текущих значениях. Для сигналов вариантов минимум три
   (`combineLatest`, `withLatestFrom`, `zip` в Rx; горячие/холодные входы Max).
   Нужен флаг «какой вход триггер» на каждый вход.
2. **Одновременность.** Данные надо сливать внутри тика (last-write-wins), чтобы D
   посчитался один раз со свежими B и C. События сливать нельзя: два клика за тик — два
   клика. Противоположные умолчания. Glitch-свобода в модели данных бесплатна из
   порядка; в сигнальной восстанавливается вручную (объекты `trigger` в Max).
3. **Отсечение по равенству.** Для данных «значение не изменилось — потомков не трогать»
   безопасно; для событий то же значение дважды — два события.
4. **Повтор при подписке и загрузке.** «Запомнить» мало: нужно ещё «переотправить
   сохранённое новому потребителю и при загрузке графа», иначе файл после открытия
   мёртв, а новая связь не оживает до изменения источника (`ReplaySubject(1)`).
5. **Чистота и повторяемость.** Из п. 4 следует: всё ниже данных может быть выполнено
   заново в любой момент — ноды данных обязаны быть чистыми. Обработчик события
   выполняется ровно один раз (HTTP POST, запись файла). Нужно знать про каждый нод,
   чистый он или нет.
6. **Зависимость от истории.** Состояние нода данных — функция текущего графа: сохранили,
   открыли, получили то же. Состояние нода, слушающего события (счётчик, «последние
   10»), — функция истории, которой в графе нет. На свойстве «состояние = f(граф)»
   держатся: протокол с пересылкой целого графа, conformance-тесты одинаковых
   результатов в Local/Worker/Server, пометка грязных по подписи нода.

## Вывод

Флагов получается семь: сохранять, какой вход триггер, сливать в тике, отсекать по
равенству, повторять при подписке, чистый ли нод, зависит ли от истории. Осмысленных
наборов два — «данные» и «сигналы». Унификация правильна внутри движка (один
планировщик, одна очередь) и вредна в модели пользователя (семь ручек, почти все
сочетания либо глитчат, либо дублируют эффекты).

Граница: два типа портов с фиксированными свойствами и явные ноды-переходники
`hold` (сигнал → данные) и `changes`/`trigger` (данные → сигнал при изменении), чтобы
переход между мирами был виден на холсте.

## Терминология

В графовых редакторах сигнальные порты называются control flow / execution ports
(exec pin в Unreal Blueprints, flow port в Unity Visual Scripting, trigger/impulse,
bang в Max). Противоположность — data port. У данных есть текущее значение, его можно
спросить в любой момент; у события значения нет, оно происходит один раз и либо
обработано, либо потеряно. Поэтому события только push: «потянуть событие» невозможно.
