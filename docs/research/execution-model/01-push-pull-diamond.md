# Push, pull и проблема ромба (2026-10-10)

## Две базовые модели

**Push (от источника к потребителям).** Изменился вход, источник сам рассылает новое
значение зависимым нодам, те пересчитываются и рассылают дальше. Минимальная задержка,
просто реализовать, естественно для потоков событий. Минусы: лишняя работа (считается
то, что никто не читает) и glitches в сходящихся зависимостях. Примеры: RxJS, Node-RED,
Max/MSP, классический observer, EventEmitter.

**Pull (от потребителя к источникам).** Нод вычисляется, когда у него запросили значение:
он спрашивает входы, те свои, и так далее; обычно с кэшем и флагом «устарел». Лениво,
считается только нужное, glitches невозможны по построению: значение запрашивается в
правильном порядке. Минусы: нужен внешний запрос; без пометки «устарел» полный пересчёт
при каждом чтении; значение должно быть синхронным. Примеры: Make, ленивые языки, Jotai,
TouchDesigner и Houdini («cook on demand»).

**Гибриды и соседи.**

- Push-pull (dirty-marking + lazy): изменение толкает вниз только флаг «устарел»,
  значение считается при чтении. Signals в Solid, Vue 3, Preact, Angular; Reactively.
- Топологический батч: изменения за тик собираются, затронутое пересчитывается один раз
  в топологическом порядке. Excel, MobX-транзакции, прежний evaluator проекта.
- Инкрементальные вычисления с динамическими зависимостями: Jane Street Incremental,
  Adapton, Salsa (rust-analyzer).
- Потоковая обработка с backpressure: Flink, Kafka Streams, Reactive Streams.
- Синхронный dataflow: Lustre, Esterel, старый Elm: весь граф на каждом такте.
- Акторы: Erlang, Akka; без глобального порядка.

## Проблема ромба

```
      A = 1
     /     \
  B = A+1   C = A*2
     \     /
   D = B + C
```

Пользователь меняет A на 10. В чистом push A обходит подписчиков по порядку подписки,
каждый сразу пересчитывается и толкает дальше.

| Шаг | Что происходит | A | B | C | D |
|---|---|---|---|---|---|
| 0 | исходное | 1 | 2 | 2 | 4 |
| 1 | A=10, уведомляет B | 10 | 11 | 2 | 4 |
| 2 | B толкает в D: D = 11 + 2 | 10 | 11 | 2 | **13** |
| 3 | A уведомляет C | 10 | 11 | 20 | 13 |
| 4 | C толкает в D: D = 11 + 20 | 10 | 11 | 20 | 31 |

Шаг 2 это glitch: D равен 13, такого значения нет ни при старых входах (4), ни при новых
(31). Последствия: лишняя работа (D считался дважды), видимый мусор в интерфейсе или в
файле, ложные срабатывания условий («если D > 12»), падение на инварианте.

**Условие шире четырёх нодов.** У нода D проблема ромба есть, если изменение выше
доходит до D по двум и более разным путям (reconvergent fan-out). Длина путей и число
поколений роли не играют. Источников может быть два разных: пользователь за один тик
поменял X и Y, оба влияют на D. Разная длина путей делает хуже: промежуточное состояние
живёт, пока считается длинная ветка. Цепочка из k ромбов даёт 2^k пересчётов последнего
нода. В чистом push финальное значение в итоге верно; проблема в промежуточных значениях,
в стоимости и в побочных эффектах, успевших сработать на мусоре.

**Как чинят.** Топологическая сортировка (нод считается после всех предков, ромбы искать
не нужно); push уведомлений и pull значений; батчинг изменений за тик. Единственное
условие для топологического порядка: граф без циклов.

## Пример Max/MSP: порядок вручную

В Max/MSP и Pure Data всё сообщения, «данных с текущим значением» нет. Чтобы считать
`a + b`, действуют три правила: левый вход объекта `[+]` горячий (пришло число, объект
считает и выдаёт), правый холодный (пришло число, объект запоминает и молчит); при
нескольких проводах из одного выхода сообщения уходят справа налево по положению на
холсте; разветвление упорядочивают явным объектом `[t …]` (trigger), рассылающим копии
строго справа налево. Без `[t]` ромб `x + x*2` даёт мусор, и это не временный glitch, а
конечный результат, потому что никто не пересчитает `[+]` заново. Урок: в чистой
сигнальной модели правильность ромба зависит от порядка доставки, и этот порядок автор
задаёт вручную в каждом месте разветвления. В модели данных с топологическим порядком или
с pull тот же ромб правилен сам по себе.

## Почему в обычном коде ромба «нет»

Четыре объекта с геттерами `b.x = a.value + 1`, `c.y = a.value * 2`, `d.sum = b.x + c.y`
это чистый pull: при чтении `d.sum` оба пути видят одно и то же A. Плата: нет
реактивности и нет памяти, каждое чтение пересчитывает всё. Код `const b = f(a); const c
= g(a); const d = h(b, c)` это ромб, где порядок строк написан вручную: текст программы и
есть топологическая сортировка. EventEmitter с подписками даёт glitch в полный рост
(второй вызов `d.recompute()` с новым B и старым C), и каждая библиотека реактивности
(digest loop в Angular 1, транзакции MobX, deferred updates в Knockout, signals) существует
именно потому, что примитивы языка проблему имеют.

## Вывод для проекта

Данные: pull с мемоизацией или топологический батч. Сигналы: только push, упорядоченный
планировщиком (очередь), а не стеком вызовов. Чистый push и «граф на инстансах классов с
вызовом методов» универсальны по выразимости, но не дают гарантий по умолчанию.
