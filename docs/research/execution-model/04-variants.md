# Варианты архитектуры вычислителя (2026-10-10)

Требования: порты данных без glitches, асинхронные ноды, задержки по времени, циклы по
сигнальным связям, детерминизм (одинаковые результаты в Local/Worker/Server), sans-IO
ядро. Требование «все ноды реактивны без запуска» (фича 001) не наследуется.

## 1. Два слоя, один планировщик: ядро данных + событийная очередь с временем

Данные — топологическим батчем или pull с пометкой «устарел». Сигналы — записи в
очереди с меткой времени: немедленные в текущий тик, отложенные ждут своего момента.
Асинхронный нод — сигнал «запрос ушёл» плюс будущее событие «ответ пришёл». Цикл по
сигналам разрешён: каждый проход по кольцу — новое событие, не рекурсия. Защита кольца
без задержки: лимит переходов за мгновение или требование задержки в цикле. Sans-IO:
движок говорит адаптеру «разбуди не позже T», адаптер зовёт `tick(now)`. Гибрид
синхронного dataflow и DEVS.

## 2. Событийная симуляция с дельта-циклами (VHDL, Verilog, SystemC)

Один механизм: очередь событий по паре (время, дельта). Связь данных — нулевая
задержка: событие в той же временной точке, следующей дельте; дельты крутятся до
затишья, затем состояние публикуется и время двигается. Связь сигнала с задержкой —
событие в будущем. Циклы без задержки — бесконечные дельты, обнаруживаются и
отвергаются. Однородно, но ромбы внутри одной точки времени дают повторные пересчёты,
пока дельты не сойдутся; лечится сортировкой событий одной дельты по топологическому
уровню — и вариант превращается в 1. Ленивости нет.

## 3. Синхронно-реактивные языки (Esterel, Lustre, Céu)

Глобальный такт; сигнал на такте присутствует или нет; данные комбинационны. Цикл
только через явную задержку (`pre`, `pause`), что проверяет анализ причинности до
запуска: редактор отвергал бы кольцо без нода задержки при создании связи, как сейчас
отвергает цикл данных. Полная детерминированность; строгость для пользователя.

## 4. Токенный dataflow и сети процессов Кана (LabVIEW, Dennis dataflow)

По связям ходят токены, нод срабатывает при токенах на всех входах; цикл требует
начального токена. По теореме Кана результат не зависит от расписания — детерминизм
бесплатно для untimed-части. Данные как «липкие» токены дают либо ожидание ненужных
обновлений, либо glitches Max. Таймеры ломают теорему. Хорошо для сигналов, плохо для
данных.

## 5. Поток исполнения + данные по требованию (Unreal Blueprints, Houdini)

Сигнал — нить исполнения по exec-связям. Задержка и HTTP — латентные ноды,
приостанавливающие нить. Циклы по exec естественны. Данные чистые, вытягиваются
(pull) в момент, когда исполнение дошло до нода; кэш с инвалидацией. Если данные
должны быть видны всегда — сводится к варианту 1 с батчем; если не должны — это
самостоятельная модель с ленивостью, и HTTP-ноды в данных не стреляют впустую.

## 6. Акторы с очередью сообщений (Node-RED, Max, Rx-граф)

Всё — сообщения, у нода почтовый ящик, таймеры и циклы встроены. Данные — «последнее
сообщение» на входе: glitches ромба и ручной порядок. Детерминизм только за счёт
однопоточной FIFO, и то не для ромбов. Полезная идея: виртуальный планировщик времени
(Rx TestScheduler) для мгновенных детерминированных тестов с задержками.

## Общее для любого варианта

- **Виртуальное время.** Движок не зовёт `Date.now`: получает `now` в `tick(now)`,
  возвращает «следующее пробуждение в T». Conformance-тесты с таймаутами мгновенны и
  одинаковы на всех хостах.
- **Поколения для асинхронных ответов.** Устаревший ответ отбрасывается, запрос
  отменяется через адаптер (`AbortSignal` снаружи ядра).
- **Защита кольца без задержки.** Лимит переходов за тик с ошибкой нода либо запрет в
  редакторе (анализ причинности). Второе предсказуемее.
- **Состояние с историей.** Очередь событий, таймеры в полёте, счётчики не выводятся из
  графа: при переподключении хоста либо теряются, либо сериализуются. Решение должно
  быть явным в spec.
- **Одновременность.** Данные, изменённые в одном тике, видны сигналам единым снимком;
  сигналы одного тика доставляются по порядку поступления.

## Выбор

Варианты 1 и 5 — одна архитектура с разным слоем данных (батч или pull). Pull общее:
политика «кого тянуть» (стоки, выделенный нод, всё) задаётся снаружи, батч умеет только
«всё». Рекомендация — вариант 5 с заимствованиями: анализ причинности из 3 для отказа в
кольце без задержки, виртуальный планировщик из 6 для тестов. Запасной — вариант 2.
