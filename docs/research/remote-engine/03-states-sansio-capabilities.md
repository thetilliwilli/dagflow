# Доставка состояний, sans-IO, возможности нодов (2026-10-07)

## Как приходят обновления состояний

- Не весь граф и не поток событий на каждый нод — **пакет изменений за один пересчёт**.
- Цикл хоста на одно изменение (`update` / `setValue`):
  1. сразу шлёт `pending { doc, rev, nodes }` — какие ноды станут `computing`;
  2. адаптер планирует `tick()` (макрозадача / `setTimeout 0`); несколько изменений,
     пришедших до тика, сливаются в один пересчёт (перетаскивание слайдера →
     десятки `setValue` → один `flush`);
  3. `flush()` синхронно пересчитывает все грязные ноды;
  4. шлёт один `states { doc, rev, states }` — только изменившиеся ноды (дельта).
- После `open` — полный снимок состояний всех нодов вкладки (тот же `states`).
- Пока `compute` синхронный, промежуточных состояний «по одному ноду» не видно: flush
  атомарный. Если появятся долгие/асинхронные ноды, хост будет слать несколько
  `states` на одну ревизию по мере готовности — форма сообщения та же.
- Клиент применяет дельты к `nodeStates` в сторе; рендер — не чаще раза за кадр.

## sans-IO

Термин из Python-сообщества (sans-io.readthedocs.io; библиотека HTTP h11). Протокол
или ядро реализуется как машина состояний: «байты/сообщения на входе → сообщения на
выходе + новое состояние». Само оно не читает сокеты, не ставит таймеры, не пишет в
консоль. Ввод-вывод делает тонкий адаптер вокруг.

```ts
// Ядро хоста (protocol): ни сокетов, ни таймеров
const host = createEngineHost();
host.receive({ type: 'open', doc: 't1', rev: 1, graph, composites });
// → [{ type: 'pending', doc: 't1', rev: 1, nodes: [...] }]
host.tick();
// → [{ type: 'states', doc: 't1', rev: 1, states: {...} }]
```

```ts
// Адаптер Node + ws
wss.on('connection', (ws) => {
  const host = createEngineHost();
  const out = (msgs) => msgs.forEach((m) => ws.send(JSON.stringify(m)));
  ws.on('message', (d) => { out(host.receive(JSON.parse(d))); setTimeout(() => out(host.tick())); });
});
// Адаптер Worker
self.onmessage = (e) => { post(host.receive(e.data)); setTimeout(() => post(host.tick())); };
// Lambda: протокол не нужен, ядро напрямую
export const handler = async ({ graph }) => { ev.setGraph(graph, []); return [...ev.flush()]; };
```

Плюсы: тесты без сокетов и таймеров (детерминированно, мгновенно); один и тот же код во
всех средах; новая среда = новый адаптер.

## API среды в нодах: не «запрещено навсегда», а «только через инъекцию»

- Сейчас все встроенные ноды чистые — им ничего не нужно.
- Будущие ноды с эффектами (HTTP, файлы, время, случайность, таймеры) не обращаются к
  глобалам напрямую. Нод объявляет нужные **возможности** (capabilities), хост/адаптер
  передаёт реализацию: `compute(inputs, ctx)` → `ctx.fetch`, `ctx.now()`.
- Нод доступен только там, где среда даёт его возможности (сервер может, njs — частично).
  Список возможностей хост сообщает в `welcome`.
- `Date.now`/`Math.random` формально есть в ECMAScript, но ломают кэш реактивного
  пересчёта (одинаковые входы → разные выходы) — тоже через `ctx`.
- Требует асинхронного `compute` и изменений вычислителя — **отдельная будущая фича**,
  в первой не делаем. Сейчас фиксируем только принцип.

## Conformance-тесты

- Цель: доказать, что собранный бандл engine + host ведёт себя одинаково в каждой среде.
- Сейчас все тесты гоняет Vitest под Node. Vitest — инструмент Node; в Bun/Deno/QuickJS
  его нет.
- Предложение: unit-тесты остаются в Vitest; дополнительно маленький самодостаточный
  скрипт сценариев (`conformance.js`: собрать граф → `open` → `tick` → сверить
  `states`, код выхода 0/1) без фреймворков. Запуск: `node`, `bun`, `deno run`,
  позже `qjs` — любая среда, умеющая выполнить файл.
