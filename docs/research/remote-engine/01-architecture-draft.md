# Удалённый engine: черновик архитектуры (v0, 2026-10-06)

## 1. Как устроено сейчас (по коду)

- `src/engine/` — чистый TS, синхронный. Две разные по смыслу части:
  - **Модель графа** (чистые функции): `createRegistry`, `nodePorts`, `canConnect`,
    `linkCandidates`, `validateGraph`, `collapse`/`expand`, `formatCompact`,
    `typeNames`, константы категорий. Ими пользуется редактор синхронно, на каждый
    жест (подсветка кандидатов на связь, палитра, отказы).
  - **Среда выполнения**: `createEvaluator` → `setGraph(graph, composites)`,
    `setValue`, `pending()`, `flush()` → `Map<nodeId, NodeState>`, `state(id)` (для
    экземпляра составного нода — сводное состояние), `stateAt(path)` (UI не использует).
- Связка: `src/store/evaluation.ts` (`startEvaluation`) — **единственное место**, где
  стор говорит с вычислителем:
  - по `Evaluator` на вкладку;
  - подписка на `workflows`/`composites`/`tabs` → `setGraph` → помечает ноды
    `computing` → `flush` раз в кадр (rAF) → пишет `nodeStates[tabId][nodeId]`.
- UI читает только `nodeStates` из стора (`FlowNode`, `PortPanels`, `PropertyGrid`) и
  про вычислитель не знает.

**Вывод**: шов уже есть. Меняется `evaluation.ts`, UI и стор почти не трогаем.
`NodeState` со статусом `computing` уже выражает асинхронность.

## 2. Целевая схема

```
┌──────────── Браузер ──────────────────────────────────────┐
│ UI (React) ──selectors──▶ Zustand store (nodeStates, conn)│
│                              ▲              │ graph changes│
│                              │ states       ▼              │
│                     EngineClient (packages/protocol/client)│
│                              │  Transport  (interface)     │
└──────────────────────────────┼─────────────────────────────┘
          ┌────────────────────┼─────────────────────────┐
     in-frame              postMessage               WebSocket
          │                    │                         │
   EngineHost            EngineHost в Worker      EngineHost в server
   (тот же поток)        (packages/worker)        (packages/server:
                                                   node/bun/deno адаптеры)
          └──────── один и тот же packages/engine ───────┘
```

- **packages/engine** — модель графа + вычислитель (как сейчас `src/engine`). Его
  импортируют и клиент (модель графа, синхронно), и хост (вычисление).
- **packages/protocol** — типы сообщений + схемы Valibot (проверка входящих),
  `EngineHost` (сервер протокола поверх `Evaluator`) и `EngineClient`. Транспорт —
  интерфейс `Channel { send(msg), onMessage(cb), onClose(cb), close() }`.
- **packages/server** — тонкие адаптеры: WebSocket ↔ `Channel` для Node, Bun, Deno +
  CLI `--port 8080 --host 127.0.0.1`.
- **app** (сейчас корень) — редактор; вместо `startEvaluation` → `startEngineConnection`.

Один `EngineHost` + один протокол на все три режима. In-frame тоже ходит через
протокол (in-memory `Channel`), чтобы путь кода был один и тестировался одинаково.

## 3. Разделение ответственности

| Где | Что |
|---|---|
| Клиент (синхронно, свой экземпляр engine) | палитра, `canConnect`, `linkCandidates`, валидация, collapse/expand, правки графа, история, хранилище |
| Хост (локально / worker / сервер) | вычисление: держит граф каждой открытой вкладки в памяти, пересчитывает, шлёт состояния |

Граф — **источник истины у клиента** (принцип III). Хост — производная копия в памяти,
которую можно потерять: после переподключения клиент отправляет граф заново.

## 4. Протокол v1 (набросок)

JSON-сообщения поверх упорядоченного дуплексного канала. Только `JsonValue` —
одинаково для postMessage и WebSocket.

### Рукопожатие
- C→S `hello { protocol: 1, engine: "<version>" }`
- S→C `welcome { protocol: 1, engine: "<version>" }` или `error { code: "version-mismatch" }`.
  Версии engine должны совпадать: клиент валидирует граф своей копией engine, хост
  вычисляет своей. Иначе типы нодов и сообщения разойдутся.

### Документы (по одному на вкладку)
- C→S `open { doc, rev, graph, composites }` — загрузить граф вкладки.
- C→S `update { doc, rev, graph?, composites? }` — новая версия структуры (целиком;
  хост сам находит изменившиеся ноды по сигнатурам, как `setGraph` сейчас).
- C→S `setValue { doc, rev, node, port, value }` — быстрый путь для правки значения
  (SC-003), без пересылки графа.
- C→S `close { doc }`.

### Состояния
- S→C `pending { doc, rev, nodes: string[] }` — что сейчас пересчитывается (`computing`).
- S→C `states { doc, rev, states: Record<nodeId, NodeState> }` — только изменившиеся
  ноды верхнего уровня (сводное состояние для экземпляров, как `state(id)`).
- S→C `error { doc?, code, message }` — ошибки протокола (не ошибки нодов: те внутри
  `NodeState`).

### Ревизии
- Клиент нумерует каждое изменение графа вкладки (`rev` растёт).
- Хост отвечает с `rev`, на котором посчитаны состояния. Канал упорядочен, поэтому
  клиенту достаточно применять сообщения по порядку. `rev` нужен, чтобы показывать
  «устаревшие» значения и для тестов (дождаться rev N).

### Почему граф целиком, а не патчи
Граф на 100 нодов — единицы-десятки КБ. Сигнатуры в `Evaluator` уже дают
инкрементальность на стороне хоста. Патчи (JSON Patch / операции) — потом, если
замеры покажут проблему (принцип I).

## 5. Связь UI с данными нодов

- UI по-прежнему читает `nodeStates[tabId][nodeId]` из стора. `EngineClient` — единственный
  писатель этого среза.
- Новый срез стора `engine`: `{ target: EngineTarget, status: 'connecting' | 'ready' |
  'offline' | 'error', message? }`. Это индикатор подключения (принцип III, обрыв связи)
  и диалог выбора.
- `EngineTarget = { kind: 'inline' } | { kind: 'worker' } | { kind: 'remote', url }`.
  Хранится в настройках браузера (это настройка, а не данные workflow).
- Обрыв: ноды показывают последнее известное состояние + общий индикатор «offline»;
  повторное подключение с паузой; после `welcome` — `open` всех вкладок заново.
- Подписки на внутренние ноды составных (`stateAt`) — не нужны сейчас (UI их не
  использует). Протокол оставляет место: `watch { doc, paths }` — потом.

## 6. Открытые вопросы

1. **Транспорт сервера.** WebSocket: в Node нет встроенного WS-сервера → либо
   зависимость `ws`, либо свой минимальный WS (RFC 6455, ~200 строк). Альтернатива —
   HTTP POST + SSE: работает без зависимостей везде, но два канала и сложнее порядок.
   Рекомендация: WebSocket; Bun/Deno — встроенный, Node — `ws` (обосновать в plan.md).
2. **Сохранять ли сессию при смене цели подключения.** При переключении inline →
   remote клиент просто открывает все вкладки на новом хосте (состояние у клиента).
3. **Размер значений.** Большие массивы в `outputs` шлются целиком при каждом
   изменении. Пока ок; позже — лимит/усечение для отображения.
4. **Несколько вкладок браузера на одном сервере.** Каждое соединение — свои
   документы, изоляция по соединению (нет многопользовательского режима).
5. **Async-ноды на сервере** (HTTP, файлы, таймеры) — вне рамок; протокол уже
   асинхронный, `compute` пока синхронный.
6. **Тесты в Bun/Deno.** В среде их нет; есть npm-пакеты `bun` и `deno` (бинарники
   как devDependency) — проверить и обосновать.
7. **SC-003** (скорость пересчёта при правке значения) — для worker/remote измерять
   отдельно; для remote — цель «на localhost».
8. **Монорепо и Vite**: приложение импортирует `@dagflow/engine` из workspace; worker —
   `new Worker(new URL(...), { type: 'module' })`, Vite собирает его сам.
