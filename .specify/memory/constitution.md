# SDD Test Constitution

## Core Principles

### I. Простота прежде гибкости (YAGNI)

- Реализуется только то, что требует текущая спецификация. Никаких «на будущее»:
  плагинов, конфигурируемости, абстракций под гипотетические сценарии.
- Новый слой, паттерн или зависимость ДОЛЖНЫ быть обоснованы конкретным требованием
  из spec.md и записаны в разделе Complexity Tracking плана.
- Из двух рабочих решений выбирается то, которое короче и проще читается.

**Зачем**: проект учебный; лишняя сложность мешает увидеть, как спецификация
превращается в код.

### II. Тесты для бизнес-логики (обязательно)

- Любая бизнес-логика (правила предметной области, вычисления, валидация) ДОЛЖНА
  быть покрыта автоматическими тестами.
- Тесты пишутся до или вместе с реализацией; задача не считается выполненной, пока
  её тесты не проходят.
- Каждый acceptance-сценарий из spec.md ДОЛЖЕН иметь хотя бы один соответствующий тест.
- Тонкий слой интерфейса (отрисовка, обработка событий) можно не покрывать отдельно,
  если логика из него вынесена в тестируемые модули.

**Зачем**: тесты — объективный критерий «готово» и для человека, и для агента.

### III. Данные у пользователя

- Workflow и другие данные пользователя хранятся только у него: в хранилище браузера
  и в файлах, которые он выгружает и загружает, в человекочитаемом формате.
- Приложение НЕ ДОЛЖНО обращаться к сторонним сервисам, облачным API или внешним
  серверам баз данных. Единственное разрешённое сетевое подключение — к серверу
  выполнения (engine) по адресу, который пользователь сам указал.
- Сервер выполнения НЕ ДОЛЖЕН сохранять данные пользователя: граф и состояние
  выполнения живут только в его памяти. После перезапуска сервера клиент заново
  передаёт ему граф.
- Отсутствие или повреждение сохранённых данных ДОЛЖНО обрабатываться явно:
  пустое состояние или понятная ошибка, но не падение и не потеря остальных данных.
- Недоступность или обрыв связи с engine ДОЛЖНЫ обрабатываться явно: пользователь
  видит состояние подключения, а работа в редакторе не теряется.

**Зачем**: приложение запускается без настройки, данные легко посмотреть и поправить
руками, а сервер выполнения можно перезапустить или заменить без риска для работы
пользователя.

### IV. Понятные сообщения об ошибках

- Каждая ошибка, видимая пользователю, ДОЛЖНА объяснять, что пошло не так и что
  делать дальше. Сырые исключения и трассировки пользователю не показываются.
- Ошибка показывается в интерфейсе рядом с местом, где она возникла (нод, связь,
  поле ввода), и не приводит к падению приложения или потере работы пользователя.
- Тексты ошибок для ожидаемых ситуаций (неверный ввод, не найден объект) проверяются
  тестами.

**Зачем**: качество продукта определяется и тем, как он ведёт себя в нештатных
ситуациях.

### V. Учебная прозрачность

- Артефакты SDD (spec, plan, tasks) ДОЛЖНЫ оставаться источником истины: если
  поведение меняется, сначала правится spec.md, затем plan/tasks, затем код.
- Код и артефакты пишутся так, чтобы новичок мог проследить путь от требования
  к реализации.

**Зачем**: цель проекта — освоить spec-driven development, а не только получить
работающую программу.

## Ограничения

- Минимум зависимостей: каждая сторонняя библиотека, в том числе серверная,
  обосновывается в plan.md (какую задачу решает и почему её не стоит писать самим).
- Продукт — веб-приложение (редактор) и необязательный сервер выполнения. Без сервера
  приложение работает полностью: по умолчанию engine выполняется в браузере.
- Engine — один пакет для всех сред: браузер (тот же фрейм и WebWorker), Node, Bun
  и Deno. В нём ДОЛЖЕН быть только стандартный ECMAScript, без API конкретной среды
  (DOM, Node API, `structuredClone` и т. п.). Различия между средами живут в тонких
  адаптерах транспорта вне engine. Работа engine в каждой из этих сред проверяется
  автоматическими тестами.
- Границы между engine, протоколом, сервером и приложением закреплены структурой
  репозитория: это отдельные пакеты монорепо.
- Без аутентификации и многопользовательского режима, если spec явно не требует
  иного (и тогда требуется поправка к конституции). Сервер выполнения рассчитан на
  доверенную сеть и по умолчанию слушает только localhost.

## Процесс разработки

- Цикл фичи: `/speckit-specify` → `/speckit-clarify` → `/speckit-plan` →
  `/speckit-tasks` → (`/speckit-analyze`) → `/speckit-implement`.
- Каждая фича ведётся в отдельной ветке `NNN-имя-фичи`.
- В plan.md раздел Constitution Check ДОЛЖЕН пройти до начала реализации; нарушения
  либо устраняются, либо явно обосновываются.
- Перед коммитом реализации все тесты ДОЛЖНЫ проходить.

## Governance

- Конституция имеет приоритет над остальными практиками и договорённостями проекта.
- Поправки вносятся через `/speckit-constitution` с описанием причины; версия
  меняется по semver:
  - MAJOR: удаление или переопределение принципа;
  - MINOR: новый принцип или раздел, существенное расширение правил;
  - PATCH: уточнения формулировок без изменения смысла.
- На шагах plan и analyze проверяется соответствие конституции; несоответствие —
  блокирующая проблема.
